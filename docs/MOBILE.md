# WARDEN Mobile

WARDEN's desktop build is Electron. Neither store accepts a bundled browser
engine, and Electron has no iOS or Android runtime, so the mobile product is a
**Capacitor shell** around WARDEN's own React surfaces with the platform engine
(Android WebView / iOS WKWebView) doing the rendering.

This document is the runbook: what exists now, what the build produces, and the
exact credentials and buttons that only the account owner can supply.

## Scope of this release

**Phase 1 (in this repository, store-ready shell):**

- Native Android and iOS projects generated by Capacitor, bundle id
  `us.innotel.warden`, display name WARDEN.
- The mobile start surface: shield-and-W splash, address field, session posture,
  quick destinations, and a statement of what is enforced.
- Pages open through the platform's private browser surface
  (`@capacitor/browser` → Chrome Custom Tabs / `SFSafariViewController`), so the
  app shares no origin, cookie jar or JavaScript context with any site.
- No analytics, crash-reporting, advertising or tracking SDKs. No account. No
  in-app purchases. No sensor access.
- Release pipelines for a signed `.aab` and an `.ipa`, plus store metadata and a
  public privacy policy.

**Phase 2 (not in this release, and the reason for calling this a shell):** an
embedded engine with per-tab isolation and content blocking. That means a custom
Android `WebView` plugin with `shouldInterceptRequest` filtering reusing
`src/main/privacy/filter-engine.ts`, and on iOS a `WKContentRuleList` compiled
from the same rule set, plus DoH via `NEDNSProxyProvider` (requires the Network
Extension entitlement and an App Review explanation). This is a native project,
not a port.

## Layout

```
mobile/
  capacitor.config.ts     app id, scheme, platform switches
  src/                    the shell UI (React + Vite)
  android/                generated Gradle project (signed in CI)
  ios/                    generated Xcode project (archive on macOS runners)
  store/android/listing.json, store/ios/listing.json
  ../.github/workflows/mobile-android.yml, mobile-ios.yml
  ../web/landing/privacy.html   public privacy policy for both listings
```

## Local development

```bash
cd mobile
npm install
npm run build          # typecheck + Vite build into dist/
npx cap sync           # copy dist/ and plugins into both native projects
npx cap open android   # needs Android Studio + SDK
npx cap open ios       # needs macOS + Xcode
```

The web shell alone runs with `npm run dev` in a browser; navigation then opens
a tab instead of the native browser surface. That is expected.

## Release builds

### Android

1. Create the upload key once (keep it out of the repository):

   ```bash
   keytool -genkeypair -v -keystore warden-release.keystore -alias warden \
     -keyalg RSA -keysize 4096 -validity 10000
   base64 -w0 warden-release.keystore > warden-release.keystore.b64
   ```

2. Add repository secrets: `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`,
   `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`.
3. Run **Mobile (Android)** from the Actions tab (or push a `v*` tag). It
   produces `warden-android-aab` with a signed bundle.
4. Play Console → your app → Testing → Internal testing → upload the `.aab`,
   add yourself as a tester, then promote.

`android/app/build.gradle` reads `android/keystore.properties` (written by CI
from the secrets); without it the build is unsigned and Play rejects it by
design.

Versioning: bump `versionCode` and `versionName` in
`mobile/android/app/build.gradle` for every upload; Play refuses a repeated
`versionCode`.

### iOS

1. Create the app record in App Store Connect with bundle id
   `us.innotel.warden`.
2. Create an App Store Connect API key (Users and Access → Integrations) with
   the App Manager role, and add repository secrets: `APPLE_TEAM_ID`,
   `APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID`,
   `APP_STORE_CONNECT_KEY_P8`.
3. Run **Mobile (iOS)**. The workflow archives on a macOS runner with automatic
   signing (`-allowProvisioningUpdates`) and uploads an `.ipa` artifact.
4. Upload it with Transporter, or
   `xcrun altool --upload-app -f WARDEN.ipa -t ios --apiKey … --apiIssuer …`,
   then attach the build to the version in App Store Connect and submit.

The App Privacy form is *Data Not Collected*; export compliance is answered by
`ITSAppUsesNonExemptEncryption = false` in `Info.plist`, so no exemption
paperwork is needed.

## Store metadata

`mobile/store/android/listing.json` and `mobile/store/ios/listing.json` hold the
text that goes into both consoles: titles, descriptions, category, contact and
privacy URLs, data-safety answers, rating expectations and review notes. Copy
them in verbatim so the two listings and this repository agree.

Icons and screenshots are the remaining graphics: 512×512 and 1024×1024 icons,
a 1024×500 feature graphic, and phone/tablet screenshots. They are not in the
repository yet; generate them from the running shell once the first internal
build exists, so the screenshots show the real UI.

## What the owner still has to do

- Google Play: account existence, identity verification and the one-time $25
  fee. The Play Console app record cannot be created by automation without that
  account, and the first `.aab` upload has to come from a signed build.
- Apple: nothing blocking, since the developer account exists. Confirm the team
  id and create the App Store Connect API key, then set the four secrets above.
- Both stores: confirm the developer name, support email and privacy-policy URL
  (`https://innotelinc.github.io/warden/privacy.html`, deployed by the Pages
  workflow from `web/landing/`).

## Non-goals

The mobile shell is not a port of the desktop browser, and it does not claim the
desktop's blocking numbers. Anything in the store listing that suggests a full
blocking browser would be inaccurate until Phase 2 lands.
